# Storm Charm — 專案提案

> **Storm Charm**：一個掛在包包上的 BLE 環境感測吊飾，持續記錄身處環境的物理量，在「感覺快下雨」的那一刻，提供實測數據作為佐證。

---

## 1. 背景與動機

走在路上有時會「感覺快下雨了」（空氣悶濕、氣壓低、突然變涼），但天氣預報的範圍較大，無法對應「此時此地」的體感，也沒有具體數據能佐證這個感覺。

現有的降雨 App 多半依賴雷達回波外推，回答的是「這個區域會不會下雨」。本專案想回答的是另一個問題：

**以目前身處的物理環境來看，現在是不是快下雨了？**

## 2. 目的

1. 製作一個隨身、低功耗的環境感測裝置，持續記錄溫度、濕度、氣壓。
2. 以「變化趨勢」而非單點絕對值，判斷降雨風險是否升高。
3. 在 App 上輸出「風險分級＋證據」，讓使用者看到判斷依據，而不是一個黑盒子的機率。
4. 作為日常可實際使用的小工具，並累積資料驗證判斷規則的有效性。

## 3. 核心概念

### 3.1 為什麼不能只看濕度

相對濕度高不等於會下雨（霧、梅雨季、海邊都可能超過 90%），單看一個數值，誤報很多。

不過歷史資料分析（見第 12 節）顯示：**濕度與露點差的「絕對值」仍是目前最強的單一訊號**（AUC 約 0.80），只是精準度有限，所以輸出採分級加證據，不給肯定的預報語氣。

### 3.2 看程度，輔以變化與多訊號

人之所以「感覺快下雨」，是在感知多個物理量的變化。本專案用感測器量化這些訊號：

| 體感 | 物理量 | 判斷方式（依 2025 臺北站逐時資料的初始值，需以吊飾資料驗證） |
|---|---|---|
| 空氣悶、黏 | 相對濕度、露點差（溫度 − 露點） | **主軸**。濕度 ≥ 85%、≥ 90%，或露點差 ≤ 2°C，分級提高風險 |
| 突然變涼 | 溫度驟降 | **加分線索**。罕見但出現時精準度高，夏季雷陣雨尤其明顯；需和濕度同時成立 |
| 氣壓低、頭悶 | 氣壓下降趨勢 | 逐時資料中**沒有預測力**，仍持續記錄，待 1～5 分鐘解析度資料驗證 |
| 遠處雷擊（後期） | 閃電偵測 | 有訊號即為強對流警訊 |

風險等級以濕度與露點差為基礎，氣溫驟降等線索只用來**加強**判斷，不單獨觸發。

### 3.3 輸出形式：分級加證據

不輸出精確的「降雨機率 73%」（假精確），而是分級並列出依據，例如：

> 注意：濕度 91%，露點差 1.6°C，溫度 15 分鐘降 3°C → 降雨風險：高

## 4. 方法與系統架構

### 4.1 設計原則：儲存後同步

吊飾是資料的主人，手機只是來讀取。

- **吊飾**：定時取樣，存入環形緩衝區，平常只做低頻 BLE 廣播（第一版只帶服務識別碼與裝置名稱，風險等級與電池放在連線後的裝置狀態）。
- **手機 App**：開啟後掃描並連線吊飾，批次下載歷史資料後斷線。
- **趨勢計算與風險判斷**：在 App 端以完整資料計算，調整門檻只需更新 App，不必重刷韌體。

這樣不需要一直連線，不佔用手機的藍牙連線額度，也較省電、不怕斷線。吊飾持續記錄，因此使用者走出門、打開 App 時，過去數小時的趨勢已經存在裝置中。

### 4.2 架構圖

```
[BME280 溫濕壓] → MCU (nRF52840) → BLE
        │ 定時取樣、環形緩衝區（相對時間戳記）
        ▼
[iPhone 網頁 App（支援 Web Bluetooth 的瀏覽器）] → 連線、批次下載歷史 → 瀏覽器本機儲存
        │ 風險計算（濕度、露點差、溫度變化；氣壓同時記錄供驗證）
        ▼
   風險分級 ＋ 證據顯示
```

### 4.3 平台選擇

- 手機為 iPhone，開發端**沒有 Mac**，因此無法開發原生 iOS App（見 4.4）。
- 第一版採**網頁 App（Web Bluetooth）**，用支援 Web Bluetooth 的 iOS 瀏覽器開啟，詳見 4.4。
- 分兩個階段：**階段 A** 先放在窗台固定蒐集資料，用電腦瀏覽器當「戰情室」同步與監看（據了解桌面版 Chrome／Edge 支援 Web Bluetooth）；**階段 B** 再搬到手機、隨身使用。同一份網頁 App 兩階段共用。
- 第一版**不需要後端伺服器與資料庫**，資料存於瀏覽器本機（並可匯出 CSV）。

### 4.4 平台限制與替代方案

**遇到的限制**

1. **沒有 Mac。** iOS 原生 App 必須用 macOS 上的 Xcode 編譯、簽章並裝到 iPhone，Windows 與 Linux 沒有官方替代，所以 Swift + CoreBluetooth 的原生路線走不通。
2. **iOS Safari 不支援 Web Bluetooth。** 在 iPhone 上，Chrome 等瀏覽器底層同樣是 Apple 的 WebKit 引擎，所以用 Chrome 開啟、或從 Safari／Chrome 加到主畫面的 PWA，都連不上 BLE 吊飾。
3. **要連藍牙，就得換瀏覽器。** 據了解，iOS 上有第三方瀏覽器（例如 Bluefy）自行補上 Web Bluetooth 支援，但必須在該瀏覽器內開啟網頁，無法從主畫面圖示啟動，且其現況與穩定性需實機驗證。

**評估過的方案**

| 方案 | 要不要 Mac | 成本 | 取捨 |
|---|---|---|---|
| **網頁 App（Web Bluetooth）＋支援它的 iOS 瀏覽器** | 不用 | 免費 | **第一版採用。** 只能在前景使用，無背景同步與通知；每次連線需手動點按 |
| React Native 加雲端建置 | 不用 | 需 Apple 開發者帳號（US$99/年，待確認） | 較接近原生，BLE 可用，流程複雜，現況需再確認 |
| 買或借 Mac，做原生 Swift App | 要 | 最高 | 功能最完整，BLE 與背景行為最好控制 |
| 筆電端 Python 同步腳本（`bleak`） | 不用 | 免費 | 備案，用於驗證階段下載資料並存成 CSV，不是手機端方案 |

**決定與理由**

- 第一版先用網頁 App，成本最低，也最快能驗證「在手機上用」是否成立。
- 本專案採「儲存後同步」：吊飾自己持續記錄，使用者打開網頁、點連線後才批次下載歷史，所以**不需要背景同步**，網頁方案對第一版夠用。
- 放棄的是主動通知，以及自動把資料累積到手機。吊飾緩衝區有上限，太久沒同步，舊資料會被覆蓋，同步頻率要配合緩衝區大小。
- 風險判斷邏輯寫成獨立、可測試的 JavaScript 模組，資料格式不綁定平台，之後換成 React Native 或原生 App 時可沿用。

**前提：先做一次實機驗證**

在 iPhone 上用 Chrome 開 Web Bluetooth 範例頁面，確認沒有藍牙功能；再用支援 Web Bluetooth 的瀏覽器開同一個頁面，確認能掃描到手邊的 BLE 裝置。這一步成立，網頁方案才成立。

**升級路徑**

若發現缺少背景同步或通知對使用影響太大，再評估 React Native 或取得 Mac 做原生 App。

## 5. 第一版規格

### 使用情境（階段 A）

- 吊飾放在不淋雨、不直曬的窗外窗台，持續蒐集資料。
- 每天用電腦網頁透過 BLE 同步一次，順便檢視電池與裝置狀態，決定要不要拿進房間；約每兩天拿進房間充電。
- 室外窗台、電腦在室內，隔著窗戶的 BLE 距離與穩定度需實測。

### 硬體

| 項目 | 選擇 | 備註 |
|---|---|---|
| MCU 板 | nRF52840 開發板（如 Seeed XIAO nRF52840） | 內建 BLE、體積小、含鋰電池充電電路 |
| 感測器 | BME280 | 溫度、濕度、氣壓，I2C |
| 電池 | 小型鋰電池（約 150～300 mAh） | 續航需實測 |
| 外殼 | 小盒或 3D 列印 | 需通風孔，遠離體溫與電池發熱 |

### 韌體

- 定時取樣（BME280 forced mode），第一版先以每 2 分鐘一筆試行
- 環形緩衝區，以開機後相對時間作為時間戳記；初步規劃放 RAM、約保留 7 天，重開機或電池沒電資料會遺失，所以至少每天同步一次
- BLE：低頻廣播；連線後提供「讀即時值」與「批次讀歷史」；資料格式與服務設計見 [`docs/data-format-spec.md`](docs/data-format-spec.md)
- 開發環境：採用 **Zephyr（nRF Connect SDK）**，在 Windows 的 WSL2 Ubuntu 中開發，兼作 RTOS 經驗累積；Arduino 為備案（環境設定卡關時，先用它把資料收起來，資料格式不變）

### 網頁 App（階段 A：電腦戰情室；階段 B：手機）

- 階段 A 的電腦版不需要手機那樣簡約，以資訊完整為主：裝置電量與電壓、連線與上次同步時間、緩衝區筆數、開機次數與運作時間、韌體版本、即時值、趨勢圖、原始資料表、匯出 CSV
- 吊飾端要配合提供「裝置狀態」，資料格式規格會分成「每筆取樣資料」與「裝置狀態」兩部分
- 畫面配置、風險等級顯示規則、趨勢圖與同步警示的草稿見 [`docs/dashboard-draft.md`](docs/dashboard-draft.md)

- HTML + JavaScript + Web Bluetooth，部署於 GitHub Pages
- 在支援 Web Bluetooth 的 iOS 瀏覽器內開啟，點按連線、批次下載後斷線
- 相對時間換算為實際時間，存入瀏覽器本機儲存（IndexedDB）
- 計算露點差與溫度變化（氣壓趨勢同時記錄、供日後驗證），輸出風險等級與證據
- 顯示即時值與趨勢圖
- 不需要 Mac，也不需要 Apple 開發者帳號

### 預估成本

硬體原型約 NT$600～1,000。

## 6. 第一版不做

後端伺服器、雲端同步、閃電偵測、光感測、「有下／沒下」標註、背景自動同步與通知、原生 iOS App。待基本版驗證後再評估。

## 7. 開發順序

1. 開發板接 BME280，以序列輸出確認讀數正常
2. 加入緩衝區與 BLE 服務，用 nRF Connect App 驗證資料可讀取
3. 開發網頁 App（Web Bluetooth）接收並顯示
4. 加入趨勢計算與風險分級
5. 放窗台持續蒐集資料，對照測站降雨紀錄調整門檻；之後再搬到手機隨身驗證

## 8. 風險與限制

| 項目 | 說明 | 因應 |
|---|---|---|
| 移動中的雜訊 | 口袋、體溫、日曬、進出室內都會干擾讀數 | 外殼設計隔熱通風；偵測劇烈環境變化時忽略該段資料 |
| 感測器反應與自熱 | 濕度感測器反應需數秒至數十秒，裝置發熱影響溫度 | forced mode 降低發熱；實測校正 |
| 門檻來自歷史測站資料 | 門檻是用固定測站的逐時資料得出，快速變化與隨身環境未驗證 | 持續記錄並與降雨紀錄對照，再調整 |
| 精準度有限 | 即使濕度 ≥ 90%，約每 4 次警報只有 1 次在 2 小時內下雨 | 輸出分級加證據，不用肯定語氣 |
| 局部對流難以預測 | 突發雷陣雨可能沒有明顯前兆 | 定位為「增加佐證」而非保證；後期可加閃電偵測 |
| 沒有 Mac | 無法編譯與安裝原生 iOS App | 第一版改用網頁 App；日後視需求取得 Mac 或改用 React Native |
| iOS 瀏覽器限制 | Safari 與 Chrome 在 iPhone 上都沒有 Web Bluetooth，須用第三方瀏覽器開啟，且無法以主畫面圖示啟動 | 先實機驗證可行；備案為筆電端 Python 同步或原生 App |
| 依賴第三方瀏覽器 | 該瀏覽器的支援度與穩定性不受控，可能變動 | 判斷邏輯與資料格式不綁定平台，方便更換 |
| 電池沒電導致資料遺失 | 緩衝區放 RAM，沒電或重開機資料會消失 | 戰情室顯示電池電壓，每天同步並依電量決定是否充電；之後評估改存 flash |
| 窗台與電腦之間的 BLE 距離 | 隔著窗戶與牆，連線距離與穩定度可能不足 | 實測；必要時把電腦或藍牙接收器移近，或改用 USB 序列同步當備援 |
| 無背景同步與通知 | 網頁只能在前景連線，且每次需手動點按 | 吊飾自己記錄，開網頁時批次下載；同步頻率須配合緩衝區大小，避免舊資料被覆蓋 |
| 續航未知 | 理論值不可靠 | 以實測為準 |

## 9. 預期成果與價值

- 一個可日常攜帶使用的降雨徵兆偵測吊飾。
- 一份自己蒐集的環境資料集，可用來驗證「哪些訊號對降雨有預測力」。
- 一個端到端的作品：感測器驅動、低功耗 BLE 韌體、網頁 App（Web Bluetooth）、資料處理與評估，適合作為 GitHub 專案展示。

## 12. 歷史資料分析（方法與結果）

在動手做硬體之前，先用氣象署測站的歷史觀測檢查：哪些訊號在降雨前真的有出現，並取得初始門檻。腳本見 [`analysis/analyze_station_rain.py`](analysis/analyze_station_rain.py)。

### 12.1 資料

- 臺北站（466920）2025 全年逐時觀測，共 8,760 筆，幾乎完整
- 欄位：測站氣壓、氣溫、露點溫度、相對濕度、降水量
- 降雨定義：逐時降水量 ≥ 0.1 mm（T 微量不算）

### 12.2 方法

1. **預測目標**：只看「當下沒在下雨」的小時，之後 2 小時內有沒有可量測的降雨。共 7,950 個小時，其中 475 個之後下雨，亂猜的基準命中率約 6%。
2. **特徵**：相對濕度、露點差（氣溫 − 露點）、露點差與濕度的 2 小時變化、氣壓 1／3／6 小時變化、氣溫 1／2 小時變化。
3. **評估方式**：
   - **AUC**：每個特徵單獨衡量區分能力（0.5 為亂猜，1.0 為完美），全年與四季分開看。
   - **精準度與涵蓋率**：預先設定門檻，看訊號觸發後的命中比例（精準度），以及所有降雨中被抓到的比例（涵蓋率）。
   - **氣壓日週期檢查**：氣壓有明顯的日週期，另外比較扣除日週期後的版本。
   - **時間切分驗證**：1～6 月訓練、7～12 月測試的邏輯迴歸，確認多特徵組合是否真的更好。
4. 門檻為事先設定，沒有針對資料調整，結果屬探索性。

### 12.3 結果

| 特徵 | AUC（全年） | 說明 |
|---|---|---|
| 相對濕度（絕對值） | **0.80** | 冬 0.86、秋 0.84、春 0.81、夏 0.74 |
| 露點差（絕對值） | **0.79** | 與濕度相近 |
| 濕度或露點差的變化趨勢 | 0.54 | 幾乎沒用 |
| 氣溫下降 | 0.52 | 整體不明顯，但見下方 |
| 氣壓下降（1／3／6 小時） | 0.46～0.51 | 等於亂猜 |

| 訊號 | 觸發 | 精準度 | 涵蓋率 |
|---|---|---|---|
| 濕度 ≥ 85% | 1,389 | 20%（基準的 3.4 倍） | 60% |
| 濕度 ≥ 90% | 586 | 26%（4.4 倍） | 33% |
| 露點差 ≤ 2°C | 795 | 24%（4.1 倍） | 41% |
| 氣壓 3 小時降 ≥ 1 hPa | 1,811 | 6%（等於基準） | 23% |
| 氣壓 3 小時降 ≥ 2 hPa | 480 | 3%（低於基準） | 3% |
| 氣溫 2 小時降 ≥ 3°C | 49 | 24%（4.1 倍） | 3% |
| 濕度 ≥ 85% 且氣溫 2 小時降 ≥ 2°C | 22 | 59%（9.9 倍） | 3% |

### 12.4 主要發現

1. **有用的是「現在有多潮」，不是「正在怎麼變」。** 濕度與露點差的絕對值最能區分，變化趨勢沒有加分。
2. **氣壓趨勢沒有預測力。** 3 小時氣壓變化的平均值隨時段約在 −1.8 到 +1.3 hPa 之間擺動（日週期），「降 1 hPa」大半反映的是時段。扣掉日週期後仍沒有訊號，方向還略微相反。這是單一測站、一年的結果。
3. **氣溫驟降罕見但精準。** 一年只觸發數十次，夏季約一半命中；和濕度同時成立時精準度更高，但只涵蓋約 3% 的降雨，樣本小，只能當線索。
4. **多特徵組合沒有更好。** 時間切分驗證：只用濕度的 AUC 為 0.807，加上全部特徵為 0.806。以逐時資料來說，濕度本身接近天花板。

### 12.5 限制與對專案的意義

- 單一測站、單一年份；測站固定且通風，吊飾是移動且受體溫影響的。
- **逐時資料會平均掉幾十分鐘內的快速變化**（氣溫驟降、氣壓快速變化），這正是吊飾 1～5 分鐘取樣要補足的部分。
- 因此歷史資料的角色是「決定先往哪裡看、設初始門檻」，最終仍以吊飾的實測資料驗證。

### 12.6 如何重跑

```bash
pip install pandas numpy scikit-learn   # scikit-learn 可省略
python analysis/analyze_station_rain.py data/taipei_466920_hourly_2025.csv --out-dir analysis/results/
```

可調參數：`--horizon`（往後看幾小時，預設 2）、`--rain-threshold`（降雨門檻 mm，預設 0.1）、`--split`（模型驗證的切分日期）。之後換測站、換年份，或把吊飾資料整理成相同欄位，都可以用同一套流程。
